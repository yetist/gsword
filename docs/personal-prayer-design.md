# GSword 全局界面与个人中心设计

- 状态：首版实施中（个人中心壳层、今日页、祷告、收获、收藏与列表已实现；书签待实施）
- 日期：2026-11-05
- 范围：全局信息架构、个人中心、祷告事项、计划/灵修/背经、收获、书签与收藏的长期规划
- 说明：本文档替代此前仅针对祷告事项的个人内容设计，并将现有“计划”页面纳入整体界面规划

---

## 1. 背景

GSword 当前的主导航是：

```text
阅读 | 对照 | 笔记 | 计划
```

其中：

- 笔记页内部有：笔记、标签、经文列表；
- 计划页内部有：今天、计划、灵修、背经；
- 祷告事项尚未实现；
- 收藏、书签、读经收获尚未实现或仅存在于设计讨论中。

如果继续按功能逐个增加主导航项，会出现：

```text
阅读 | 对照 | 笔记 | 计划 | 祷告 | 收藏 | ...
```

主导航会变成功能清单，窄窗口和底部导航模式也会迅速拥挤。与此同时，笔记和计划内部已经出现多层标签，继续叠加会让个人内容分散在多个地方。

因此需要从全局重新规划信息架构，而不是单独决定“祷告放在哪个标签”。

## 2. 设计目标

### 2.1 核心目标

1. **阅读优先**：启动后仍然直接进入经文阅读。
2. **主导航保持精简**：主导航不超过 3 个内容空间。
3. **个人内容集中管理**：笔记、祷告、计划、灵修、背经、收藏、书签、收获统一进入“个人”中心。
4. **概念清晰**：笔记、祷告、列表、书签、收藏、高亮、计划各自有明确语义。
5. **可扩展**：未来增加新个人功能时，不需要继续增加主导航项。
6. **可渐进实施**：先迁移现有页面，再增加新功能，避免一次性大重写。

### 2.2 非目标

首轮不实现：

- 云同步和多人共享；
- 祷告提醒和后台通知；
- 复杂的计划模板市场；
- 跨设备收藏同步；
- 全功能日记/灵修出版工具。

## 3. 新的全局信息架构

### 3.1 主导航

主导航缩短为 3 个空间：

```text
阅读 | 对照 | 个人
```

搜索和模块库继续作为标题栏全局动作，不占主导航：

```text
[搜索] [模块库] [主菜单]
```

这样：

- 阅读和对照保持直接可达；
- 所有个人内容进入“个人”；
- 模块库仍可从标题栏和模块侧栏进入；
- 搜索仍保持全局快捷入口。

### 3.2 个人中心二级导航

“个人”页面内部使用二级导航：

```text
今日 | 笔记 | 祷告 | 计划 | 收藏与列表
```

对应英文：

```text
Today | Notes | Prayer | Plans | Collections
```

每个二级区域内部再按需要设置子标签：

| 个人区域 | 子标签/内容 |
|---|---|
| 今日 | 继续阅读、今日计划、今日灵修、祷告摘要、背经复习、最近笔记 |
| 笔记 | 笔记、标签、读经收获 |
| 祷告 | 进行中、已应允、已归档、全部 |
| 计划 | 计划管理、灵修、背经 |
| 收藏与列表 | 经文列表、书签、星标收藏 |

### 3.3 整体示意

```text
┌──────────────────────────────────────────────────────────────┐
│ 阅读  对照  个人                         [搜索] [模块] [菜单]│
├──────────────────────────────────────────────────────────────┤
│            今日 | 笔记 | 祷告 | 计划 | 收藏与列表           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                      当前个人区域内容                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

个人中心只面向宽屏桌面；窄窗口不作为支持目标，二级导航不再提供下拉或横向滚动降级方案。

## 4. 各区域设计

### 4.1 阅读

阅读页保持现有习惯：

- 整章阅读；
- 书卷/章/节路径栏；
- 阅读历史；
- 阅读外观；
- 专注模式；
- 研经侧栏；
- 当前经文上下文菜单。

不把个人内容管理放进阅读页主体，只保留快捷入口：

```text
添加到笔记
添加到祷告
添加到经文列表
添加书签
```

### 4.2 对照

现有对照工作区保持不变：

- 1–4 个对照栏；
- 同步滚动、固定、独立模式；
- 差异高亮；
- 布局保存。

未来如果需要更复杂的研经工作区，可继续放在“对照”内部，而不是增加新主导航。

### 4.3 今日

“今日”是个人中心的默认首页，用于聚合当天的行动，而不是替代各管理页面。

建议卡片：

```text
继续阅读
  KJV · Genesis 1:1

今日计划
  第 12 天：马太福音 5–7

今日灵修
  今天的灵修内容摘要

祷告
  3 条进行中祷告

背经复习
  2 节待复习

最近笔记/收获
  ...
```

每个卡片都可以点击进入对应区域。这样原来“计划页里的今天”被提升为个人中心首页，减少“计划页既是计划管理又是每日首页”的混杂。

### 4.4 笔记

笔记区域保留并整理现有内容：

```text
笔记 | 标签 | 收获
```

- **笔记**：绑定经文的个人注释；
- **标签**：笔记标签管理；
- **收获**：自由形式的读经心得、讲道摘录、灵修体会，可关联经文，也可以不关联。

经文列表从笔记区域移动到“收藏”区域，因为它是个人经文集合，不是笔记。

### 4.5 祷告

祷告区域使用独立双栏页面：

```text
┌──────────────────────┬───────────────────────────────────────┐
│ 搜索祷告...           │ 为家人祷告                            │
│ 状态：[进行中 ▾]      │ 状态：[进行中 ▾]                      │
│                      │ 关联经文：腓 4:6-7                    │
│ 为家人祷告            │ 标题：____________________________    │
│ 进行中 · 11-05        │ 正文编辑器                            │
│ 为工作祷告            │ ...                                   │
│ 已应允 · 10-28        │ 应允备注                              │
│                      │ [保存] [标记已应允] [归档] [删除]      │
│ [+ 新建祷告]          │                                       │
└──────────────────────┴───────────────────────────────────────┘
```

状态：

- 进行中；
- 已应允；
- 已归档。

祷告事项可以有零节、一节或多节关联经文。提醒和祷告日志时间线放在后续阶段。

### 4.6 计划

计划区域收纳现有计划页的功能：

```text
计划管理 | 灵修 | 背经
```

- **计划管理**：计划列表、创建、模板、进度、重命名、复制、删除；
- **灵修**：每日灵修内容阅读；
- **背经**：待复习队列、卡片模式、复习记录。

原来的“今天”标签内容迁移到“个人 → 今日”页面；计划区域不再承担每日首页职责。

### 4.7 收藏与列表

收藏与列表区域集中管理所有“保存起来以后查看”的内容：

```text
经文列表 | 书签 | 星标收藏
```

- **经文列表**：用户自定义命名集合，如“主日讲道”“查经主题”；
- **书签**：阅读位置，记录“读到哪里”，可带备注；
- **星标收藏**：一键星标的单节经文集合，是系统默认列表。

如果首版暂不实现书签和星标收藏，收藏与列表区域先只显示经文列表，并为后续扩展保留位置。

## 5. 概念边界

| 功能 | 语义 | 是否绑定经文 | 是否有状态 | 主要用途 |
|---|---|---|---|---|
| 笔记 | 对某节经文的注释 | 是 | 否 | 研经记录 |
| 收获 | 自由形式心得或摘录 | 可选 | 否 | 灵修、讲道、读书收获 |
| 祷告 | 有生命周期的代祷事项 | 可选 | 进行中/已应允/已归档 | 祷告管理 |
| 经文列表 | 用户自定义经文集合 | 是 | 否 | 主题整理 |
| 书签 | 阅读位置 | 是 | 否 | 回到阅读位置 |
| 收藏 | 快捷星标的单节经文 | 是 | 否 | 快速保存喜欢的经文 |
| 高亮 | 经文视觉标记 | 是 | 否 | 阅读标记 |
| 计划 | 按日期推进的读经安排 | 是 | 有进度 | 读经计划 |
| 灵修 | 每日灵修内容 | 可能是 | 否 | 灵修阅读 |
| 背经 | 待复习经文队列 | 是 | 有复习状态 | 背经训练 |

### 5.1 笔记和收获的区别

- 笔记必须依附于具体经文；
- 收获可以是一段自由文字，也可以选择关联一节或多节经文；
- 收获更适合记录“今天读经最大的领受”“一篇讲道的要点”，不强迫挂到单节经文上。

### 5.2 经文列表和收藏的区别

- 经文列表可以有多个、可命名、可自由组织；
- 收藏是一个默认系统集合，强调一键星标；
- 收藏底层可以复用 `verse_lists`，增加 `kind = favorites` 或 `is_system` 标记，避免维护两套 membership 逻辑。

### 5.3 书签和阅读历史的区别

- 阅读历史自动记录，最多保留一定数量；
- 书签由用户显式创建，可带标题/备注，不自动淘汰；
- 书签是“值得再次回到的位置”，不是普通历史记录。

## 6. 数据模型规划

祷告、收获、书签和收藏都使用现有 `app.db`，但保持独立表或复用明确的系统结构。

### 6.1 祷告

```sql
CREATE TABLE IF NOT EXISTS prayers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  body TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active',
  created INTEGER NOT NULL,
  updated INTEGER NOT NULL,
  answered_at INTEGER,
  answered_note TEXT
);

CREATE TABLE IF NOT EXISTS prayer_entries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  prayer_id INTEGER NOT NULL REFERENCES prayers(id) ON DELETE CASCADE,
  body TEXT NOT NULL,
  created INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS prayer_verses (
  prayer_id INTEGER NOT NULL REFERENCES prayers(id) ON DELETE CASCADE,
  module TEXT NOT NULL,
  key TEXT NOT NULL,
  display_key TEXT NOT NULL,
  PRIMARY KEY (prayer_id, module, key)
);
```

### 6.2 收获

```sql
CREATE TABLE IF NOT EXISTS insights (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL DEFAULT '',
  body TEXT NOT NULL DEFAULT '',
  created INTEGER NOT NULL,
  updated INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS insight_verses (
  insight_id INTEGER NOT NULL REFERENCES insights(id) ON DELETE CASCADE,
  module TEXT NOT NULL,
  key TEXT NOT NULL,
  display_key TEXT NOT NULL,
  PRIMARY KEY (insight_id, module, key)
);

CREATE TABLE IF NOT EXISTS insight_tags (
  insight_id INTEGER NOT NULL REFERENCES insights(id) ON DELETE CASCADE,
  tag TEXT NOT NULL,
  PRIMARY KEY (insight_id, tag)
);
```

### 6.3 书签

```sql
CREATE TABLE IF NOT EXISTS bookmarks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL DEFAULT '',
  module TEXT NOT NULL,
  key TEXT NOT NULL,
  display_key TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT '',
  created INTEGER NOT NULL
);
```

书签保存的是阅读位置，不是经文集合成员。

### 6.4 收藏与列表

星标收藏和经文列表建议统一使用现有表：

```text
verse_lists(id, name, kind)
verse_list_items(list_id, module, key, display_key)
```

新增字段：

```sql
ALTER TABLE verse_lists ADD COLUMN kind TEXT NOT NULL DEFAULT 'normal';
```

约束：

- 只允许一个 `kind = 'favorites'` 的系统列表；
- 星标收藏列表不可删除；
- 普通列表可以创建、重命名、删除。

如果当前尚未发布，也可以直接在新 schema 中一次建好 `kind` 字段，不需要迁移。

## 7. 页面与代码结构

### 7.1 页面对象

建议最终结构：

```text
window.c
├── reader_page
├── workspace_page
├── search_page
├── personal_page
│   ├── today_page
│   ├── notes_page
│   ├── prayer_page
│   ├── plans_page
│   └── collections_page
└── library_page
```

- `personal-page` 负责个人中心的二级导航和子页面组装；
- `today-page` 聚合今日卡片；
- `prayer-page` 管理祷告事项；
- `plans-page` 整合现有计划、灵修、背经；
- `collections-page` 整合经文列表、书签、收藏；
- `notes-page` 保留现有笔记和标签，收获后续加入；
- `window.c` 只负责页面注册、共享服务和跨页面跳转。

### 7.2 页面 ID 和设置

建议页面 ID：

```text
reader
compare
personal
personal/today
personal/notes
personal/prayer
personal/plans
personal/collections
```

`active-page` 需要兼容：

| 旧值 | 新值 |
|---|---|
| `notes` | `personal/notes` |
| `plan` | `personal/plans` |
| `panes` | `compare` |

因为项目尚未正式发布，可以不做长期兼容，但开发环境和已有设置应至少做一次映射，避免启动后找不到页面。

### 7.3 跨页面服务

需要新增类似服务：

```c
void gsword_window_show_personal(GswordWindow *self,
                                 GswordPersonalSection section);
void gsword_window_open_prayer_for(GswordWindow *self,
                                   const gchar *module,
                                   const gchar *key,
                                   const gchar *display_key);
```

阅读器、搜索、今日卡片都通过窗口服务跳转，不直接操作 `PersonalPage` 私有状态。

- 收获创建和搜索。

### 9.3 兼容性测试

- 旧 `active-page=notes` 映射到 `personal/notes`；
- 旧 `active-page=plan` 映射到 `personal/plans`；
- 旧经文列表仍可读取；
- 旧笔记、高亮、计划数据不受影响。

## 10. 关键决策

1. **主导航缩减为 3 项**
   阅读、对照、个人。搜索和模块库继续作为全局动作。

2. **“计划”不再是一级页面**
   计划、灵修、背经进入个人中心，由“计划”区域管理和展示。

3. **“今日”成为个人中心首页**
   聚合阅读、计划、灵修、祷告、背经和最近笔记，而不是放在计划页内部。

4. **笔记和祷告分开建模**
   笔记绑定经文；祷告有状态、应允时间和独立编辑器。

5. **经文列表和收藏分开**
   列表是用户自定义集合；收藏是唯一系统星标集合，底层复用列表 membership。

6. **书签是位置，不是列表**
   书签与阅读历史、经文列表、收藏都不同。

7. **收获是自由形式内容**
   收获允许不绑定经文，解决“有心得但不想挂到具体一节”的问题。

## 11. 首版范围建议

如果希望分阶段落地，建议第一版只做：

- [ ] 个人中心壳层
- [ ] 主导航缩减为 3 项
- [ ] 现有笔记页迁入个人/笔记
- [ ] 现有计划页迁入个人/计划
- [ ] 今日页面基础卡片
- [ ] 祷告事项 CRUD

收藏、书签、收获可以后续按阶段实施，避免一次性重构过大。

## 12. 风险

- 主导航缩减会影响用户已有的页面习惯，需要迁移 `active-page`；
- 个人中心只面向宽屏桌面，二级导航不提供窄窗口响应式方案；
- 祷告、书签、收获、收藏都在个人中心，页面内部导航层级不能过深；
- `notes-page` 当前已经是较大的页面对象，迁移时要避免继续膨胀；
- 多个 store 同时打开同一个 SQLite 文件，需要统一 `busy_timeout` 和错误处理；
- 书签和阅读历史、收藏和经文列表之间有语义重叠，UI 文案必须明确。

## 13. 结论

建议采用：

```text
主导航：阅读 | 对照 | 个人

个人：今日 | 笔记 | 祷告 | 计划 | 收藏与列表

笔记：笔记 | 标签 | 收获
计划：计划管理 | 灵修 | 背经
收藏与列表：经文列表 | 书签 | 星标收藏
```

这个结构把现有“计划”的个人属性纳入统一规划，同时为祷告、书签、收藏和收获预留了稳定位置，不需要继续增加主导航项。
